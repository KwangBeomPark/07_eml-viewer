# 07 EML Viewer Windows 성능 개선계획

작성: 2026-10-12. Codex 총괄, Claude Opus 5.5 계획 검수,
초기 Gemini 연결 검수 이후, 2026-10-13 사용자 지시로 Gemini 호출을 중단하고
GPT-6 Luna 하위 구현·Codex 통합·Opus 5.5 최소 2회 검수로 진행한다.

## 목표와 범위

Python/PySide6 구조에서 첫 화면, 메일 전환, 큰 첨부파일 처리의 지연을 줄인다.
2026-10-13 사용자 지시에 따라 이 개선계획은 Python으로 진행하며 C#으로 바꾸지
않는다. 이번 계획에 C++/C# 전면 재작성, 서명, 설치, 릴리즈 게시를 포함하지 않는다.

원본 EML/MSG, UserSetting, 설정 이관·손상 보호, 첨부파일 차단·MOTW,
외부 이미지 기본 차단, PDF 인쇄, 기존 릴리즈를 보존한다. 벤치마크는 합성
메일과 격리된 임시 디렉터리만 사용한다. 외부 모델에 사용자 메일을 보내지 않는다.

## 작업 방식

1. Codex가 한 단계의 대상 파일과 완료 기준을 정한다.
2. Opus 5.5가 설계·순서·회귀 위험을 검수한다. 모델 입력은 필요한 소스만 포함한다.
3. GPT-6 Luna에 파일 소유 범위를 나눈 작은 구현/회귀/측정 작업을 맡긴다.
4. Codex가 실제 소스와 응답을 대조하고 최소 변경을 구현한다.
5. 관련 회귀와 `pytest tests`를 실행하고 같은 데이터로 성능을 비교한다.
6. 이 파일의 상태·수치·제한을 갱신한 뒤 다음 단계로 진행한다.
7. 통합 후 Opus 5.5 검수를 최소 2회 받고 발견 사항을 수정한다. 필요하면 추가
   검수하고, 마지막 두 번째 검수와 최종 검증은 Codex가 마무리한다.

CLI 종료 0이나 `SUCCESS`만으로 완료 처리하지 않는다. 빈 응답, 시간 초과,
부분 출력, 모델/에이전트 fallback을 구분한다. 완전한 보고서와 고유 완료
표식을 검사하고 실제 테스트는 Codex가 따로 검증한다. 한 번에 여러 성능
변경을 섞지 않으며 변화가 없거나 기능이 깨지면 해당 변경을 채택하지 않는다.

단계 2의 후보는 `AttachmentService.save_attachments`가 첨부마다
`EmlParser.extract_attachment`를 부르고 그때마다 원본을 다시 해석하는 구조다.
전역 메일 캐시를 먼저 추가하지 않고 일괄 저장 작업 한 번의 수명 안에서
해석 결과를 재사용해 캐시 무효화·다중 창 메모리 문제를 줄인다.
선택 payload만 생성기로 반환하며 요청 순서·중복 인덱스를 보존한다.
MSG는 기존 추출 경로를 유지하고 성능 개선 대상에서 제외한다.

Opus 제안대로 1a/1b를 분리하고 2.5 프로파일 단계를 추가했다. 연결 구성(0)이
실패해도 제품 성능 작업을 자동 중단하는 선행조건으로 삼지 않는다.

단계 3의 백그라운드화는 화면 응답성 개선과 실제 처리시간 개선을 구분한다.
QThread만으로 Python CPU 연산이 빨라진다고 가정하지 않는다. 공유 parser의
상태, 오래된 결과 배제, i18n, 실패 안내, 앱 종료와의 경합을 설계에 포함한다.

단계 5는 창만 빨리 뜨고 HTML 내용은 더 늦어지는 결과를 성공으로 세지 않는다.
현재 트레이/싱글 인스턴스/HTML 사전 초기화 및 공유 프로필과의 관계를 확인한다.

## 측정 규칙

- 소스 해석·첨부 추출 microbenchmark와 설치형 EXE 시작 측정을 따로 기록한다.
- 입력 파일 크기, 첨부 개수·크기, 반복 횟수, Python/PySide6 버전, git 기준을 남긴다.
- 소수 반복은 중앙값과 범위만 보고한다. p95를 주장하려면 최소 20회 반복한다.
- 첫 실행은 독립 프로세스, 반복 열기는 같은 프로세스로 구분한다.
- 성능 후보의 채택 기준은 관련 경로의 반복 측정 개선과 기능 회귀 통과다.
  시작·HTML·RSS·UI 반응성 개선 수치는 각각 실제로 측정한 경우에만 기록한다.
- MSG는 실제 합성 MSG fixture가 확보되기 전에는 mock 기능 회귀와 EML 측정만
  구분해 기록한다. EML 결과를 MSG 성능으로 일반화하지 않는다.
- offscreen Qt 검사는 실제 데스크톱의 시각적 반응성/인쇄/설치 증거가 아니다.

### 2026-10-12 첫 구현 결과

- Opus 계획 검수: Python 유지, 작업 단위 생성기, MSG 기존 경로 유지 제안 채택.
  실제 응답은 `build/external-agents/20261012T214639Z-38927c09/`에 있다.
- Gemini 소스 검수: 호출 체인·반복 해석·CID/덮어쓰기/MOTW 회귀 제안 확인.
  모든 payload를 사전에 dict로 디코드하는 제안은 피크 메모리와 부분 실패 계약
  때문에 채택하지 않았다. 기록은 `build/external-agents/20261012T214617Z-06c2a8de/`.
- 이름 있는 inline text의 기존 인덱스 버그: 새 회귀가 수정 전 `body.txt`를
  잘못 추출하는 실패를 재현했다. 단건 추출의 본문 텍스트 제외 규칙을 화면과
  맞춘 뒤 관련 20개 테스트가 통과했다. 이후 별도로 일괄 저장 최적화를 적용했다.
- `iter_extracted_attachments`: EML 원본 1회 해석, 비선택 첨부 디코드 생략,
  중복 선택 결과 재사용, 마지막 사용 후 해제. parser 인스턴스 상태는 추가하지 않았다.
- Opus 사후 검수: 첨부 추출 PASS(발췌 범위), CLI 래퍼에서 로그 없는 fallback
  수용 위험과 Windows cmd shim 위험 지적. 로그·모델 라벨·agent 활성화 확인과
  Windows native EXE 선택으로 보완했다. 모든 소스를 검수한 것으로 과장하지 않는다.
- CLI 최소 에이전트 확인: 실제 등록된 Gemini의 무도구 요청은 입력 3,056 토큰,
  약 43.7초. 기본 에이전트 요청 입력 약 26,074 토큰과 구분한다. 입력 컨텍스트는
  줄었지만 시작 지연은 남았으며 비용·속도 우위나 계정 청구 절약을 단정하지 않는다.

같은 합성 입력 각 5회, Windows 11/Python 3.13.14, warm 파일 캐시의 중앙값:

| 대상 | 변경 전 | 변경 후 | 확인 범위 |
| --- | --- | --- | --- |
| 512 KiB 첨부 6개 일괄 저장 (EML 약 4.34 MB) | 325.208 ms, 원본 해석 6회 | 64.711 ms, 원본 해석 1회 | 약 80.1% 시간 감소, 저장 SHA-256 일치 |
| 8 MiB 첨부 1개 저장 (EML 약 11.42 MB) | 213.980 ms | 142.499 ms | 약 33.4% 시간 감소, 1회 해석 유지 |
| plain 파싱 | 2.426 ms | 2.387 ms | 파싱 경로 최적화 수치로 주장하지 않음 |
| HTML 파싱 | 27.858 ms | 27.069 ms | HTML 표시·시작 속도 수치가 아님 |

원본 측정 JSON은 `build/performance-planning/baseline.json`과
`after-bulk.json`. baseline의 제품 소스는 git `6bd846a` 상태이고, after는 이번
미커밋 제품 변경을 포함한다. 이후 벤치마크는 제품 소스 SHA-256도 기록한다.
작은 횟수의 중앙값 비교이며 p95·실제 사용자 메일·MSG·전체 앱 성능의 증거가 아니다.

회귀 범위: 기존 테스트 및 첨부 요청 순서·중복·CID·비ASCII 이름·0바이트·중첩
메시지·비선택 디코드·부분 실패·MOTW 호출·MSG 기존 추출 경로. CLI 검증은 빈/부분
응답·timeout·fallback·모델/활성화·완료 표식 검사다. 전체 테스트 수치는 최종 확인 후
아래에 기록한다. GPU 관련 offscreen 경고를 실제 Windows 시각 검수 성공으로 세지 않는다.

- 최종 `pytest tests`: **238 passed, 36 subtests passed**, 7.45초. 고유 build/ 임시
  테스트 디렉터리를 사용했다. 기존 공용 pytest-current 잠금 오류를 우회하며
  사용자 임시 디렉터리를 삭제하지 않았다.
- 제품 소스 SHA-256을 추가한 최종 재측정: 첨부 6개 저장 중앙값 **65.746 ms**
  (64.083–74.196 ms), 원본 1회 해석. 최초 개선 후 64.711 ms와 같은 수준의
  개선을 확인했다. 8 MiB 단건 중앙값은 158.649 ms로 실행 간 변동이 있어
  단건 효과를 일괄 저장의 약 5배 개선과 혼동하지 않는다.
  최종 JSON: `build/performance-planning/after-bulk-final.json`.
- `git diff --check` 통과. 전역/프로젝트 Gemini 정의 내용 일치, `agy agents`에서
  등록 확인. 실제 기본 에이전트 fallback 검출과 등록된 에이전트의 High 모델
  선택·소스 검수·무도구 요청 완료를 각각 확인했다.
- 당시 다음 단계는 **2.5 메일 열기 경로 프로파일**이었다. 이후 구현과 검수는
  아래 2026-10-13 기록을 따른다.

### 2026-10-13 통합 결과

GPT-6 Luna 3개 작업을 Codex가 통합했다. Python 유지, 비동기 메일 열기,
폴더 cache/watch, HTML 엔진 지연 생성을 구현했다. Opus 5.5 통합 검수 2회와
추가 검수 2회의 지적 사항을 고친 뒤 Codex가 최종 2차 점검을 마무리했다.
전체 **293 passed, 40 subtests passed**, 실제 HTML/CID PDF source smoke 통과.
측정·모델 응답·수정 전 NOT PASS·최종 Codex 수정·남은 runtime 경계는
[통합 기록](PERFORMANCE_OVERNIGHT_20261013.md)에 남긴다.

설치형 EXE 기준선(1b) 대신 먼저 합성 source widget 및 실제 HTML marker 완성
시간을 측정했다. 이 측정은 설치형 기준선을 대체하지 않는다. plain PDF는
offscreen에서 기존 HEAD·현재·직접 Qt 문서 모두 검은 막대가 나타나 실제 GUI
확인이 필요하다. Windows 설치·서명·배포, physical printer, 네트워크/교차 볼륨
TEMP 실제 환경과 OS cold start/RSS는 다음 게이트로 남긴다.
